# Resumable member photo and video uploads — source candidate v36

The authenticated phone app can select JPEG, PNG, MP4 and MOV files individually or from a SAF folder. Selection builds a private review with file count, aggregate byte count, skipped-file count and a metered-network warning. A batch contains at most 100 accepted files and 64 GiB; folder paths stay on the phone. The app hashes each original by streaming, sends one file at a time, persists only account-scoped transfer metadata and URI grants, and resumes only after a person taps Resume. Leaving the app or changing account pauses transfer.

The server's new `access_upload_transfers` table is migration-owned and requires revision `a8d4c2e6f901`. The migration adds a transfer ledger to revision `f2a6d8b4c915`; no application startup creates tables. The offline operator path requires an exact separate backup, fingerprint review, all writers drained and explicit execution. Existing accounts, memberships and upload receipts must survive unchanged. No live migration or service activation is claimed by this source change.

`POST /upload-sessions` creates or retrieves an idempotent account-bound transfer using a 32-character request ID and batch ID, basename, positive byte count, full SHA-256 and `image` or `video` kind. Images are capped at 256 MiB and videos at 16 GiB. `PUT /upload-sessions/{id}` requires a matching committed offset, SHA-256 for its at-most-4-MiB octet-stream chunk, and an active approved membership. `GET` reports the committed offset; `POST /complete` and `DELETE` complete or cancel. The completion receipt is durable and idempotent, including after a reply is lost or the upload is approved. A wrong offset returns 409 and requires status reconciliation. Only the current account can address its transfer. Cookie writes require CSRF; native requests use bearer credentials. The old `POST /uploads` remains available for older photo clients with its 25 MiB cap.

Each transfer has an OS-held file lock. A chunk is fsynced before its offset advances. An uncommitted tail is truncated on retry. Two transfer bodies or completions can run at once per API worker; bodies never exceed 4 MiB in application memory. Completion verifies the whole SHA-256 by streaming, checks a bounded image header or ISO BMFF box structure, then writes the incoming asset and completed transfer state in one database transaction. A structurally accepted video is not yet a decoded or prepared video. The worker runs strict bounded `ffprobe`, then at most 32 scaled keyframes, an embedding and a caption. Failed decoding remains a failed task; it must not create a synthetic success vector. Frame extraction is bounded by time, output size and owned-process cleanup. Video face detection is not wired into this path.

Completed files remain in the account's private incoming area with no library mapping. The owner/operator reviews and assigns them. Video review shows an explicit pending-preview placeholder instead of sending original video bytes into the photo preview decoder. Assignment does not itself publish to anonymous TV access or guarantee prepared playback; the existing prepared-media pipeline remains a separate step. Transport admission, staging disk capacity, backlog and failed video tasks should be checked before a live rollout. Partial `.transfers` data is removed on confirmed cancellation; abandoned transfers have no automatic garbage-collection policy yet and require an operator review before cleanup.
