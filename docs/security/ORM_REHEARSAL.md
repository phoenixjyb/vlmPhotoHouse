## Implemented

`app.access.metadata.migration_metadata()` builds a combined copy of legacy ORM
metadata plus all eleven access/admission tables. Alembic uses that combined copy.
The original `db.Base.metadata` remains unchanged, so legacy `create_all` callers
cannot create security tables or replace explicit security migrations. The HTTP
entry point continues to import neither SQLAlchemy nor runtime configuration.

Real Alembic autogenerate comparison, including defaults, produces **zero access
schema differences** after the current migration chain. Constraint, primary-key,
foreign-key and index declarations match the explicit SQLite DDL, including
SQLite's existing nullable reflection of INTEGER PRIMARY KEY columns.

The migration environment now requires an explicit URL or supplied connection.
The hardcoded Windows database default was removed from `alembic.ini`. A supplied
connection wins over DATABASE_URL, preventing synthetic/embedded calls from being
redirected by an unrelated environment value. No `.env` is loaded.

SQLite migrations enable foreign keys before a transaction and use an actual
BEGIN IMMEDIATE transaction for DDL and the Alembic revision ledger. A caller's
existing transaction remains caller-owned; the standalone URL runner owns and
commits its own transaction. Injected failures roll back both schema and revision
state. Offline SQL output is explicitly unsupported because these revisions inspect
the database; it is not described as a safe migration rehearsal.
